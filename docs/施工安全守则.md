# 施工安全守则（附：虚拟滚动裁决）

给家里的麦穗：这页两件事——一个技术裁决，一套防止施工模型把家拆了的纪律。

## 裁决：虚拟滚动不做

理由：虚拟滚动（DOM 回收 + 动态高度 + 滚动补偿）是为"几万条起步"的列表准备的，我们一个会话几百到几千条，浏览器直接渲染没有压力。而我们的气泡全是动态高度（Markdown、图片、工具折叠盒），正是虚拟滚动最难伺候的形态。收益接近零，风险全额保留——否决。

**替代方案（做这个）：分段渲染**

- `openSession()` 只渲染最近 50 条；更早的存在内存里不上 DOM
- 消息区顶部放一个「查看更早的 50 条」按钮，点击往上补一段
- 补入时保持视野不跳：记录补入前的 `scrollHeight`，补完把 `scrollTop` 加上差值
- 不做滚动到顶自动加载（滚动事件就是坑本坑），就用按钮
- 服务端不用改，整段历史照常返回，切片在前端做

改动只涉及 `public/app.js` 的 `openSession()` 附近，几十行的事。

## 防拆家纪律（每次让施工模型干活前照做）

上次 Opus 把代码搞坏修了一上午，根因不是它菜，是没系安全绳。以下每条都是绳：

1. **动工前先落一个安全点**：`git add -A && git commit -m "施工前存档"`。这一步做了，搞坏的代价就是一句 `git checkout -- .`（回到存档），永远不存在"修一上午"。
2. **坏了就回滚，不原地抢救**：改坏的代码上继续缝补，十次有九次越缝越破。回到安全点，缩小任务范围，重来。
3. **一次只干一件事**：给施工模型的指令里写明"只改 XX 文件的 XX 部分，其他文件一律不动，不要顺手重构、不要改格式、不要动没让你动的东西"。它爱发挥，就要用缰绳。
4. **改完先验收再提交**，验收三板斧：
   - `npm run typecheck`（服务端类型）
   - `node --check public/app.js`（前端语法）
   - 跑起服务真发一条消息，走通一轮
5. **每项独立提交**，提交信息中文写清楚。这样任何一次 `git log` 都能定位是哪一步引入的问题，`git revert` 单独撤掉它。
6. **红线**：`server/engine.ts` 的人设注入逻辑、WS 协议已有字段、鉴权逻辑——没有明确需求不碰。

把第 3 条那句"只改 XX、其他不动"养成每次派活的口头禅，能挡掉八成事故。
